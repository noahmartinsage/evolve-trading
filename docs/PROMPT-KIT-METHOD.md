# 项目 → 技术开发提示词套件 · 通用方法论与模板

> **本文是母版，`DEV-PROMPT-KIT.md` 是实例（EVOLVE 项目）。**
> 想对任意项目产出同款提示词套件，按本文流程走一遍即可。
>
> **版本**：v2 · 2026-09-12 —— 骨架从 7 Part 扩到 **10 Part**（新增 H 服务层 / I 验证层 / J 文档治理），
> 流程从 5 步扩到 **6 步**（新增 Step 6 定期复检）。v2 的改动全部来自对 EVOLVE 实例的实际复检：
> 项目长大后，那三个 Part 会自然长出来，而**复检**是发现"文档已经跟不上代码"的唯一手段。

---

## 一、这套文档到底在解决什么问题

普通的「项目总结 / README」写的是 **What**（项目是什么、有哪些模块）。
但 AI 复现项目时失败的真正原因，从来不是不知道 What，而是：

1. **不知道 How 的约束条件** —— 哪个库必须锁版本、哪个 API 有隐藏陷阱
2. **不知道 Why-not** —— 哪些写法看起来合理但会炸，前人已经踩过了
3. **不知道边界** —— 哪些功能是真的、哪些只是演示占位

所以一份合格的提示词套件必须包含**三层信息**：

| 层 | 回答什么 | 对应 Part | 缺失后果 |
|---|---|---|---|
| **What** | 项目是什么 | Part B 架构梳理 | AI 能写，但写跑偏 |
| **How** | 怎么复现 | Part A/C 提示词 | AI 写不出来或写错 |
| **Why-not** | 为什么不能那样写 | Part F 避坑清单 | **AI 必踩坑，且反复踩** |

> 💡 **核心判断**：Part F（避坑清单）是整份文档复用价值最高的部分。
> 架构能从代码读出来，坑读不出来。如果时间只够写一块，写 Part F。

## 二、标准文档骨架（13 Part）

```
Part A  一键复现主提示词     ← 可整段复制投喂，自包含
Part B  架构梳理             ← 定位边界 / 架构图 / 技术栈 / 目录树 / 设计令牌
Part C  分层复现提示词       ← 每层一段独立提示词（L0 骨架 + L1..Ln）
Part D  关键契约速查         ← 常量表 / 配置值 / API 契约 / 环境变量，要求"一字不差"
Part E  安全与风控红线       ← 不可协商的硬约束
Part F  已知问题与避坑清单  ← ★ 编号 F-1..Fn，每条含 症状/后果/正确写法
Part G  验收清单 + 执行顺序  ← 可勾选的 Checklist
Part H  后端/服务层提示词    ← ★ 若项目有独立服务进程，这一层与 C 同等重要
Part I  验证层与 CI          ← ★ 门禁清单 + 测试契约 + 验证纪律
Part J  文档治理地图         ← ★ 多文档项目的权威出处与冲突解决规则
```

**为什么是这个顺序**：A 放最前是因为它是唯一"拿来即用"的部分；
F 放靠后但权重最高，因为它是经验的沉淀；G 是给复现者的终点。
H/I/J 是**项目长大后追加的**（见 Step 6）——它们回答的是另外三个问题：

| Part | 回答的问题 | 什么时候必须加 |
|---|---|---|
| **H** | "后端怎么复现" | 项目出现独立服务进程（不只一个前端） |
| **I** | "凭什么相信它是对的" | 出现自动化测试/CI 门禁 |
| **J** | "哪份文档说了算" | 文档超过 3 份且开始互相矛盾 |

> ⚠️ **不要一开始就写满 10 Part**。首次梳理时 H/I/J 往往还不存在；
> 强行写会产出空话。它们是**随项目成长按需追加**的（触发条件见表）。

## 三、执行流程（梳理一个项目的 6 步）

### Step 1 · 扫骨架（10 min）

```bash
# 目录树 + 依赖版本
cat package.json          # 或 pom.xml / requirements.txt / go.mod
find src -type f | sort   # 只看业务代码，排除 node_modules
find server -type f | sort  # ★ 别忘了后端：它常在视野之外却体量惊人
```

产出：技术栈表（**版本要精确，不要写 "最新版"**）、目录树。

> ⚠️ 版本必须锁到 minor。写 `^18.3` 而不是 `React 18`，写 `wagmi ^3.7.6` 而不是 `wagmi`。
> 大版本差异（如 wagmi v2 → v3）会让整套提示词失效。

> ⚠️ **实测教训（EVOLVE）**：首次梳理时漏看了 `server/`，并在文档里写成"后端不在本仓库"。
> 13 天后复检发现后端有 **30 文件 / 4623 行**，与前端体量相当。
> （上句是**当时快照**；2026-09-12 复检时已增至 **35 文件 / 8873 行**——
> 这个数字本身又漂了一次，正好再次印证本节主题。）
> **教训：`find` 要覆盖所有顶层目录，不要假设"这是个前端项目"。**

### Step 2 · 读核心文件，识别分层（30 min）

按「数据流向」而非「目录名」分层。典型分层：

```
数据源层 → 状态层 → 业务/算法层 → UI 层
```

对每个候选分层问三个问题：
- 它的**输入**来自哪里？（外部 API？用户操作？上一层？）
- 它的**输出**到哪里去？（状态？下一层？UI？）
- 它**失败时**怎么办？（降级？抛错？重试？）← 这条最容易被漏，但 AI 复现时最需要

### Step 3 · 提取契约（20 min）

把所有"改一个字符就会崩"的东西单独抄出来：

- 合约地址 / API endpoint / 端口
- 精度与单位（decimals、毫秒 vs 秒、百分比 vs 小数）
- 阈值与常量（min 值、上限、版本号）
- 环境变量名

> 💡 这一步能顺手发现 bug。**版本号类常量最容易出现"A 处定义、B 处硬编码"的不一致**。
> （EVOLVE 就是这么发现 `fitness-v2` vs `fitness-v1` 的。）

### Step 4 · 挖掘坑位（30 min，最重要）

坑不会写在代码里。四个来源：

| 来源 | 怎么找 |
|---|---|
| **版本迁移陷阱** | 库的大版本 Upgrade Guide。如 wagmi v3 改了 `useBalance` 签名 |
| **隐式默认值** | 看起来能省略的参数。如 `parseUnits(x)` 默认 18 位，USDC 是 6 位 |
| **历史 bug** | git log 里搜 fix/revert/wrong；对话历史里搜"之前报错" |
| **环境差异** | 公共服务的稳定性差异。如某 RPC 返回 521，另一个正常 |

**每条坑按这个格式写**：

```markdown
### 🐛 F-n · 一句话标题（已修复 / 现存 Bug）

**症状**：界面上看到的现象
**后果**：实际造成了什么损失（数字越具体越好）
**正确写法**：```代码块```

修复状态要标清楚——「已修复，勿再犯」和「现存待修」对复现者的意义完全不同。
```

> ⚠️ **"后果"一定要写具体**。写"金额会算错"没人当回事；
> 写"3000 USDC 被解析成 3000×10¹²，界面显示 $5.7M"才会被记住。

### Step 5 · 成文与自检（20 min）

写完后过一遍自检表（第六节）。

### Step 6 · 定期复检（re-audit）· ★ 最容易漏掉的一步

**这不是一次性的工作。** 项目会继续长，而文档不会自己跟着长。
实测（EVOLVE）：首版文档产出 13 天后复检，发现——

| 漂移类型 | 实例 |
|---|---|
| **事实错了** | 文档称"后端不在本仓库"，实际后端 4623 行就在仓库里 |
| **版本过期** | 文档写 Vite `^5.3.4`，实际 `^8.2.2` |
| **规模过期** | 文档写"13 道门禁"，实际 16 道 |
| **新事实未收录** | 新增 30 个后端文件、11 个前端组件完全不在文档中 |
| **状态过期** | 文档标注的"待修 bug"早已修好，却仍在验收清单里挂着 `[待修]` |

> ★ **这条最容易被忽略，也最容易复发。** EVOLVE 在 2026-09-12 又犯了一次：
> `AUTOPILOT_LIVE` 默认值缺陷**当轮已修**，文档却继续记为「⏳ 待决」——
> 而且犯错的正是「重新梳理项目、完善文档」这个动作本身。
> 原因很朴素：**梳理时沿用了上一份缺陷清单的结论，没有逐一回到运行时复验**。
> 判据只有一个：**跑一次、看行为**。清单不是事实，文档也不是。
>
> 附带教训：**"已修的坑"和"没修的坑"必须分开记**。EVOLVE 的 F-15 修完后仍留着一半真实风险
> （代码默认值已安全，但本机 `.env` 显式开了实盘），若只写「✅ 已修」就会漏掉后半句。
> 所以修复记录要写成**两行**：代码层达成了什么、部署层还剩什么。

**复检动作清单（每次 30–60 min）**：

```text
1. 重新 find 目录树，与 Part B4 逐行对比 —— 找"文档里没有的文件"
2. 重跑所有 npm scripts（lint / typecheck / test:*) —— 找"文档说绿实际是红"的
3. grep 文档里的每个具体值（端口/版本号/阈值/门禁数），回源码核对
4. 读最新 5~10 个改动文件，找新增的坑位
5. 检查验收清单里有无已修复项仍标 [待修]
6. 看文档数量是否已超过 3 份 → 触发 Part J（文档治理）
```

> ★ **核心心法：代码 > 文档**。复检时**不要相信文档**，包括你自己上次写的。
> 每一个断言都回到源码或 `npm run` 实测确认。发现冲突时**以代码为准并修改文档**。

> ⚠️ **为什么必须有这一步**：量化/金融类系统的漂移不是"文档不好看"的问题。
> EVOLVE 复检时发现 `AUTOPILOT_LIVE` 的默认值是 `'true'`（即裸启动走实盘路径），
> 而这条事实从未被任何文档记录——**一次复检就避免了一个真实资金事故**。
>
> ★ **这条教训还有个"第二层"**（EVOLVE 2026-09-12 亲历）：该缺陷修复后，
> 文档**又反向漂移了一次**——代码已改，文档仍写"待决"。所以复检要**双向**：
> 不只查"代码有没有踩文档没写的坑"，还要查"文档报的坑代码是不是已经填了"。
> 判据只有一个：**运行时行为**，不是任何一份清单。

## 四、各 Part 写作要点

### Part A 主提示词

- **自包含**：不依赖读者看过文档其他部分
- **含负面约束**：明确写"不要用 X""不要引入 Y"。AI 对负面指令敏感度低于正面指令，所以要用加粗/列表强化
- **含验收信号**：告诉 AI 什么状态算成功（如"构建零错误""看到真实价格跳动"）

模板：
```text
你要从零构建一个 [项目名]，这是 [一句话定位]。
## 技术栈（版本锁定，不要升级大版本）
- ...
## 分层架构（按此顺序实现，逐层验收）
第1层 ... 第2层 ...
## 硬性红线（不可协商）
1. ...
## 交付要求
- ...
```

### Part B 架构梳理

- **必须写「能力边界」章节**，用 ✅ / ⚠️ 区分"真实现了"和"只是演示"。
  这是防止后人（和 AI）夸大系统能力的关键。
- 架构图用 ASCII，不要依赖图片（图片会失效、无法 diff）
- 目录树只列关键文件，用 ★ 标注核心文件

### Part C 分层提示词

每层的提示词必须包含：
1. 用什么技术（含版本陷阱）
2. 关键决策与**为什么**（如"统一 USDC 计价，避免 USDT/USDC 基差误导"）
3. 已知会踩的坑（直接内联，或引用 Part F 编号）
4. 该层的验收信号

> 💡 分层提示词要能**独立使用**。有人只想复现第 3 层，不该被迫读完全文。

### Part D 契约

表格优先，标注"勿改"。开头写一句"复制时保持一字不差"。

### Part E 红线

用「不可协商」语气。每条红线要说明**违反会怎样**（资金损失？数据泄露？）。
金融/交易类项目至少覆盖：模式隔离、不跨会话恢复危险态、模拟通道、最小输出保护。

### Part F 避坑清单 ★

见 Step 4。额外要求：
- 编号连续 `F-1 ... F-n`，方便跨文档引用
- 标题里带状态：`（已修复，勿再犯）` / `（现存 Bug，优先修）`
- 按"后果严重度"排序，不要按发现顺序

### Part G 验收清单

- 每条必须**可观测**（"报价约 0.8 ETH"而不是"报价正确"）
- 包含**数量级校验**（如"不是 2980 ETH"）——数值类 bug 靠数量级最容易暴露
- 末尾附推荐执行顺序（先做什么最有成就感、什么依赖什么）

### Part H 后端/服务层提示词（若有独立服务）

**判断是否需要**：存在独立进程（`server/`、`api/`、`worker/`），且它有前端没有的能力。

写法与 Part C 同构，按 **L6 / L7...** 编号延续，但内容重心不同：

- **先写"为什么必须独立成服务"**（L6.0）。这段比代码重要——不写清楚，
  复现者会把服务端逻辑塞回前端，架构就塌了。
- **每个模块一段提示词**，含"检查顺序"这类**顺序即安全**的细节。
  例：风控检查必须"熔断先于频控"，因为限流会掩盖爆仓信号。
- **单例/契约类模块**（网关、适配器）要把**状态字段与检查链**逐条列出，
  它们是"最后一道物理闸"，含糊描述等于没有。

### Part I 验证层与 CI（若有自动化测试）

**判断是否需要**：存在 `npm run ci` / CI workflow / smoke 测试。

必写三块：
1. **门禁清单表**：每道门禁"守护什么"，而不是"命令是什么"
2. **⚠️ CI 与本地的一致性检查**：实测 EVOLVE 的 GitHub workflow 只跑 5 道，
   本地 `npm run ci` 跑 26 道——**两套清单必然漂移**
3. **验证纪律**（可直接作为提示词投喂）：改哪类代码要跑哪几道门禁、
   "任一道红灯即停，修完重跑全链，禁止只重跑通过的那几道"

### Part J 文档治理地图（若文档 > 3 份）

**判断是否需要**：`docs/` 下超过 3 份文档，且出现同一事实多种说法。

必写三块：
1. **权威范围表**：每份文档"说了算的范围"是什么（一张表）
2. **冲突解决优先级**：★ 第一条永远是 **`源码与实测 > 一切文档`**
3. **收敛建议**：识别职责重叠的文档并给出合并建议

> ★ 最高频的漂移源：**同一事实在 N 份文档里各复述一遍**。
> 纪律是「**每个事实只允许一个权威出处，其余文档用引用而非复述**」。
> 例：端口只写在 `.env.example`，其他文档一律写"见 .env.example"。

## 五、通用空模板

复制下面这段，填入你的项目内容：

```markdown
# [项目名] · 技术开发提示词套件（可复用）

> **源项目**：[路径]
> **生成日期**：[日期]

## 使用说明（四档用法）
| 用法 | 场景 | 怎么做 |
|---|---|---|
| A. 全量复现 | 从零重建 | 复制 Part A |
| B. 分层复现 | 只做某层 | 复制 Part C（前端）/ Part H（服务端）对应层 + Part D 契约 |
| C. 二次开发 | 加功能 | 读 Part B + Part F |
| D. 验收/接盘 | 判断能否上线 | 读 Part I + Part J，先跑门禁再信文档 |

# Part A · 一键复现主提示词（Master Prompt）
[自包含提示词]

# Part B · 架构梳理
## B1 定位与能力边界    ← ✅ 已实现 / ⚠️ 边界，必须写
## B2 架构总览          ← ASCII 图
## B3 技术栈与版本      ← 锁到 minor
## B4 目录结构          ← ★ 标核心文件（含 server/ 等所有顶层目录）
## B5 设计令牌          ← 如有设计系统

# Part C · 分层复现提示词（前端/主体）
## L0 工程骨架
## L1 [第一层]
...
# Part D · 关键契约（复制时保持一字不差）
## D-n 常量/地址表
## D-n API 契约
## D-n 环境变量契约      ← ★ 单一权威出处，其他文档引用此处
# Part E · 安全与风控红线（不可协商）
# Part F · 已知问题与避坑清单   ← ★ 最高优先级
# Part G · 验收清单 + 执行顺序

# Part H · [服务端]层复现提示词（L6..）  ← 有独立服务进程才写
# Part I · 验证层与 CI                   ← 有自动化测试才写
# Part J · 文档治理地图                  ← docs/ 超过 3 份才写
# Part K · 多智能体/多角色协作            ← 用 LLM 做决策才写
# Part L · 对标与内化                    ← 做过外部项目对标才写
# Part M · 生产级交付与实测序列          ← 涉及真实资金/真实用户才写
```

## 六、成文自检表

写完后逐项打勾，不打勾别交付：

**准确性**
- [ ] 所有版本号精确到 minor，且与实际 `package.json` 一致
- [ ] 所有地址/端口/常量是**从源码复制**的，不是凭记忆写的
- [ ] 架构分层反映的是**实际数据流向**，不是目录名
- [ ] 每条 F-n 坑都验证过确实存在（能 grep 到，或有历史记录）

**完整性**
- [ ] Part B1 明确区分了 ✅ 真实现 与 ⚠️ 演示占位
- [ ] Part D 覆盖了所有"改一个字符就崩"的常量
- [ ] Part E 覆盖了所有会造成实际损失的操作
- [ ] Part G 每条都可观测、含数量级校验

**可用性**
- [ ] Part A 自包含，脱离文档也能用
- [ ] 每层 Part C 提示词可独立使用

## 九、LLM 提示词模板库

> **合并自原 `PROMPT_ENGINEERING.md` 的第二部分**（该文档其余部分已被 `DEV-PROMPT-KIT.md` 的 Part B 覆盖，故删除）。
> ⚠️ **已按当前代码事实校正**：原模板引用 `fitness-v1` 与 2 个策略族，现为 `fitness-v2` 与 6 个策略族。
> 照抄旧模板会让模型产出与引擎不匹配的字段——**这是模板类文档最容易腐烂的地方**，
> 所以每个模板都注明了「哪些值是必须实时读取的、不能硬编码」。

### 9.1 与 Part A 的区别（先分清两类提示词）

本套件里有两类完全不同的提示词，**不要混用**：

| | Part A 的复现提示词 | §九 的 LLM 提示词 |
|---|---|---|
| 读者 | 帮你写代码的 AI Agent | **你系统运行时的模型** |
| 目的 | 复现一个项目 | 让模型在既定边界内做决策/提案 |
| 生命周期 | 一次性 | 常驻，每轮调用都要用 |
| 关键约束 | 技术栈、架构、红线 | **输出契约 + 实时边界** |

**§九 的三条铁律**（比模板本身重要）：

1. **输出契约必须机器可校验。** 永远返回结构化 JSON，且 `version` 字段必填。
   模型自报的 `id`、`kind` 之类字段**一律不信任，由引擎强制校正**——
   EVOLVE 实测中 `deepseek-v4-flash-free` 首次调用即因 proposalId 非法被拒。
2. **实时边界必须插值，不能硬编码。** 见 9.6。
3. **必须提供降级路径。** 模型调不通时退回确定性引擎，绝不卡死主循环。

### 9.2 模板 0 · 系统提示词（策略研究员 / 提案器身份）

> 用途：所有下游任务的常驻 System Prompt。
> **注意**：`fitness_version`、`engine_version` 等字段必须从代码常量插值，**不要写死在提示词里**。

```text
你是 EVOLVE 系统的「策略研究员（提案器）」。

# 身份与边界（最高优先级）
- 你是研究辅助，不是交易员。你**只能输出结构化策略变异/调参提案**。
- 你**没有任何下单、签名、链上操作权限**，也**不得**生成任何可直接执行的交易指令。
- 你的每条提案都将被人类或确定性引擎门禁审核后，才可能被回测与晋升。
- 若数据缺失或工具不可用，必须输出「降级」结论，不得编造行情、收益或成交数字。

# 你工作的世界（事实，不可篡改）
- 策略是确定性纯函数，签名：decide(ctx) -> {side, type, price?, frac} | null。
- 适应度函数（版本号由引擎注入，你只能理解不能改）：
    它奖励「高收益/回撤比 + 低换手」，对换手有开方级惩罚。
- 撮合成本假设：maker 2bps、taker 5bps、滑点 3bps、成交量参与上限 10%、延迟 1 根 K 线。
- 用户消息中的【本周期风险预算】是**执行层实时硬约束**。你的提案参数必须落在其声明的边界内；
  越界提案不会被「尝试执行」，而是被物理拦截并降级为 WAIT。

# 输出契约（永远 JSON，version 字段必填）
{
  "schema_version": "<由引擎注入>",
  "engine_version": "<由引擎注入>",
  "fitness_version": "<由引擎注入>",
  "data_version": "<数据来源标识>",
  "reasoning": [ "<短句，最多 6 条，对齐 UI 推理轨迹风格>" ],
  "proposals": [ <见模板 1 的 proposal 结构> ],
  "degraded": <bool>
}

# 推理轨迹风格（少样本）
- 「分析 4H 结构：多头通道完好，1H ADX 26 属有效趋势」
- 「生成候选变异：将入场阈值由 80 下调至 76，以提升样本量」
- 「回测 24h 历史 · 期望收益 +2.1% / 最大回撤 -0.4%」
- 「评估风险预算：当前 R:R 底线 2.0，本提案 R:R=2.3，通过几何校验」
- 「风控官复核：单笔风险 0.5%，未越集中度上限，放行」
```

### 9.3 模板 1 · 变异提案（Mutation Proposal）

> 输入 = 精英策略 + 回测报告 + 种群停滞信号；输出 = N 条结构化变异提案。

```text
# 任务
基于以下「精英策略 + 回测报告」，提出 {{N}} 条**只改参数、不改策略家族**的变异提案。
每条提案必须可被执行引擎直接实例化并回测。

# 当前精英策略
family: {{family}}            # 六个策略族之一，具体清单由引擎注入
params: {{params_json}}
fitness: {{fitness}}
fitness_version: {{fitness_version}}
report: {{report_json}}       # totalReturnPct/annReturnPct/sharpe/maxDrawdownPct/tradesPerDay/...

# 种群上下文
generation: {{gen}}
stagnation_streak: {{streak}}      # 连续无增长的代数；>=3 触发本次深度搜索
population_avg_fitness: {{avg_fitness}}

{{risk_brief}}                     # ← 由 riskBrief 渲染的【本周期风险预算】块

# 约束
- 每条提案只能对现有 params 做**有界** delta，边界见上方风险预算块。
- 必须给出可被回测证伪的 hypothesis，以及 risk_note。
- 不得引入引擎不支持的新指标或新家族。

# 输出（proposals 数组元素结构）
{
  "family": "<家族名>",
  "base_params": { ... },
  "param_deltas": { ... },
  "rationale": "<为什么这么改，一句话>",
  "hypothesis": "<可被回测证伪的预期，含量化区间>",
  "expected_effect": "<换手/胜率/回撤 预计怎么变>",

}
```

### 9.4 模板 2 · 策略诊断 / 弱点归因（Critique & Diagnostics）

> 闭环反馈：把回测报告回喂给模型，解释「为什么 fitness 低 / 哪里崩了」。
> 作用是把单调的数字翻译成**人类可行动的洞见**，喂回模板 1 形成进化循环。

```text
# 任务
给定一条策略的回测报告，输出「最可能的 1~2 个致命弱点」+ 对应修复方向（仍只产出提案，不下单）。

# 输入
family: {{family}}
params: {{params_json}}
report: {{report_json}}
fitness: {{fitness}}   (version: {{fitness_version}})

# 分析框架（强制覆盖，缺一项视为未完成）
1. 收益质量：annReturnPct 是否被少数极端 bar 拉动？sharpe 是否靠低波动虚高？
2. 回撤来源：maxDrawdownPct 发生在什么行情结构？（用 horizonDays 与 tradesPerDay 推断）
3. 成本侵蚀：手续费相对换手名义额的占比？taker 占比是否过高（说明限价单用太少）？
4. 过拟合嫌疑：winRatePct 虚高但 annReturnPct 低，是否存在小赚大亏？

# 输出
{
  "verdict": "overfit | cost-heavy | whipsaw | drawdown-prone | healthy",
  "weaknesses": [ "<一句话弱点>" ],
  "fix_directions": [ "<对应提案方向，参数级>" ],
  "confidence": 0.0~1.0
}
```

### 9.6 模板 5 · 本周期风险预算块（**必插，不可省**）

> 这是 R20 内化带来的关键模板，也是最容易被漏掉的一块。
> **没有它，模型只能凭先验猜门槛，产出的提案会被物理拦下而它无从修正。**

```text
【本周期风险预算】
（生成时刻 {{ts}}。以下为执行层当前**实时**硬约束，与引擎同一数据源；
 任何不满足的报价会被物理拦截并降级为 WAIT，不会被「尝试执行」。请在此边界内做决策。）

· 最大并发持仓：{{max_concurrent}} 笔（同向最多 {{max_same_dir}} 笔）
· 单笔风险额（1R）：可用权益的 {{risk_per_trade_pct}}%
· 盈亏比硬底线：R:R ≥ {{min_rr}}（低于此值直接拒单，无例外）
· 开仓置信度门禁：≥ {{min_confidence}}%
· 杠杆区间：{{min_lev}}x ~ {{max_lev}}x
· 止损几何：结构失效点之外 {{atr_min}}x ~ {{atr_max}}x {{atr_period}} 周期 ATR
· 保本移损：浮盈 ≥ {{breakeven_r}}R 时把止损拉至成本位 +{{breakeven_buf}}%
· 金字塔加仓：{{scale_in_clause}}
```

**三条实现纪律**：

1. **必须读活绑定，不能读表单默认值。** 读 DEFAULTS 表会得到「面板显示的值」
   而非「引擎执行的值」——这正是要消除的分裂。
2. **加仓被禁用时必须明文写「不得申请加仓」**，否则模型仍会产出必然被拒的加仓申请。
3. **措辞必须声明「会被物理拦截」**，不能只说「建议遵守」。模型需要知道越界的后果是拒绝而非尝试。

> **验证方法**：加一条断言，检查渲染出的文本里包含实时阈值。
> 这类「两套口径」的回归只有靠断言才能挡住——人工 review 不会注意到一个数字悄悄分叉了。

### 9.7 模板复用清单（照抄前先核对）

| 模板 | 必须实时注入的字段 | 常见腐烂点 |
|---|---|---|
| 0 系统提示词 | 所有 `*_version` | 版本号硬编码 |
| 1 变异提案 | `risk_brief`、家族清单、参数边界 | 家族清单过期 |
| 2 弱点归因 | 报告字段名 | 报告结构改了但模板没改 |
