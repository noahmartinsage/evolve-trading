## §1 · 为什么对标 R20（同构性论证）

对标的前提是两者在**同一个问题上给出不同解法**。先确认这一点成立：

| 维度 | R20 | EVOLVE | 是否同构 |
|---|---|---|---|
| 核心命题 | 策略随时间自动迭代，替代静态网格/均线 | 自进化引擎 + 晋升流水线 | ✅ 同构 |
| 进化周期 | 每 6 小时一轮自进化 | Autopilot 自治循环（按 K 线巡检） | ✅ 同构（周期策略不同）|
| 决策主体 | LLM 交易主脑 + 参谋委员会 | LLM 提案器 + Agent 团队 | ✅ 同构 |
| 风控形态 | 物理拦截插件（Python，热插拔） | 拦截闸门管线（TS，内置） | ⚠️ 同构但可配置性差一档 |
| 执行场所 | OKX（CEX） | Binance REST/WS（行情）+ Uniswap V3（链上） | ❌ 不同（我们多一层链上）|
| 风控参数来源 | `risk_constants.py`（SSOT） | `riskConstants.ts`（SSOT） | ✅ 同构 |
| 提示词与代码口径 | 每轮插值 `【本周期风险预算】` | 静态 SYSTEM_PROMPT（**内化前**） | ✅ 同构 |

**结论**：在「第 4 层决策大脑自进化」这一层，R20 与 EVOLVE 解决的是同一类问题，
且 R20 在**可配置性**与**账本语义严谨性**上明显更成熟。这部分值得直接内化。
而在链上执行、审计治理、准入治理三块，EVOLVE 走得更远——**不能因为对标就自我否定**（见 §3 反向项）。

### 2.3 三个值得学的设计细节

**① 插件契约极简，可执行文件即接口**

```python
# R20 的插件契约——就这一个函数
def check_risk(package: dict, decision: dict, context: dict) -> tuple[bool, str]:
    return True, ""   # (是否放行, 拒绝原因)
```

插件元数据写在**文件开头的 docstring 里**（id/name/version/description/tags），
管理器解析它来渲染后台列表。**没有注册表、没有基类、没有装饰器**——
用户丢一个 `.py` 进目录就能用。这是「低门槛热插拔」能做到的关键：
约束越少，非工程师越敢写。

**② 核心地板 + 插件管线的分层拦截**

`run_interceptor_pipeline()` 先跑**不可绕过的确定性检查**（数据完整性、方向冲突、
报价几何、全局 R:R ≥ 2.0、置信度门禁），再依次跑用户插件。
关键在顺序：地板在前，插件在后——用户插件**无法通过排序把自己提到地板之前**。

**③ 每轮把风控口径插值进提示词**

`ai_brain_trader.py` 每周期把「最大并发持仓 / 同向上限 / 单笔风险额 / 杠杆区间 /
置信度门禁 / R:R 底线 / ATR 止损区间 / 加仓门禁」实时渲染成 `【本周期风险预算】` 块
放进用户消息。措辞里明确「不满足将被执行层拒绝」，让模型在自己的决策空间里看到边界。

## §4 · 已内化清单（5 项）

> 内化原则：**学语义，不抄实现**。R20 是 Python + sqlite3（同步阻塞 + 线程锁），
> EVOLVE 是 Node + `node:sqlite` + 单线程事件循环。
> 同样的语义在两边的最优实现不同，照抄会引入不属于本项目的复杂度。

### 4.1 组合风险预算原子预留层 → `server/riskReservation.ts`

**为什么必须内化**：这是本项目 `LEDGER_MISMATCH` 的**根治方案**，不是锦上添花。
历史上账本对不上有两类成因，R20 的做法各给一个对策：

| 成因 | 朴素做法 | R20 做法 |
|---|---|---|
| A. 本地追踪器一消失就当作仓位不存在 | 清掉记录、释放额度、下一轮重复开仓 | **未知状态显式化**：`unknown`/`pending`/`partial` 一律全额占用，只有确认终态才释放。**「本地丢了」≠「场所没有」** |
| B. 「查额度 → 判断 → 写入」之间有窗口 | 并发路径各自读到旧总额，双双通过检查 | `BEGIN IMMEDIATE` 把三步包成原子操作，越界**整体回滚，绝不部分占用** |

**落地形态**：
- 状态词表 6 态：占用态 `pending`/`partial`/`unknown`/`confirmed`，终态 `rejected`/`closed`
- **`confirmed` 仍占用**——确认成交到平仓之间风险依然真实，提前释放会让后续开仓重复计入
- 终态**幂等不可复活**：已释放的意图再提交 `reserve` 原样返回，不改写
- 孤儿恢复 `recoverOrphans()` **只标记 `pending_cleanup` 不释放**，等对账器拿到场所侧确定结论再显式释放
- 跨所合看 `grossExposure(environment)` / `totalReservedByVenue()`——**合看风险，不混资金**
- 账户键 `{venue, environment}` 建模，paper 与 live 预算天然隔离
- 自治循环接线：**预留先行 → 发单 → 按回执推进**。发单前落账，崩溃重启后 `recoverOrphans` 仍能找到
- 失败分类 `classifyOrderFailure()`：只有场所**明确拒绝**才释放；适配器缺失/握手未完成/超时一律记 `unknown` 继续占用

**内化过程中抓到并修掉的一个自造缺陷**：`occupying` 字段原本写成
`!released && OCCUPYING_STATES.has(state)`，而 `pending_cleanup` 不在 `OCCUPYING_STATES` 里，
导致孤儿记录金额仍计入 `totalReserved`、`occupying` 却报 `false`——**台账与视图两套口径**。
本模块存在的意义就是消除这类分裂，不能自己制造一个。现判据统一为 `released` 标志，与 `totalReserved` 完全同源。

### 4.2 决策证据可观测性分档 → `server/decisionObservability.ts`

**为什么内化**：「有决策日志」和「日志能用来复盘」是两件事。一条记录带 20 个字段、
其中 18 个是 `null`，仪表盘上很充实，但事后无法回答「当时为什么这么判」——
这种记录会**静默污染自进化样本**：LLM 把空壳当证据，从噪声里总结出「心法」。

**落地形态**：
- 四档：`DYNAMICS_OBSERVED` / `PARTIAL` / `PRICE_ONLY` / `NONE`
- `DYNAMICS_FIELDS` 只收**解释价格为何这样动**的字段（ATR/ADX/结构位/动能），
  **不收 price**——只知道价格不知道波动与趋势强度，无法归因
- 边界处理：**0 与 false 是有效值**（ADX=0 表示趋势极弱，是真实观测）；`NaN`/`Infinity`/空串算缺失
- `pruneSnapshot()` 剔除 null/undefined，不让模型在 22 个 null 里自行数证据
- `isSampleQualitySufficient()`：**数量与可归因占比必须同时达标**，
  防止「30 笔全是空壳」被当作足够样本去提炼心法
- 自治循环在 `AUTOPILOT_POSITION_OPENED` 事件里落盘决策时刻快照 + 分档标签
  （regime 是 5 分钟 TTL 滚动缓存，不落盘则复盘时读到的是当下的市场，不是决策时的市场）

### 4.3 策略政策快照与一键回滚 → `server/policySnapshot.ts`

**为什么内化**：策略行为由**四份彼此独立的配置**共同决定——风控参数、心法库、
拦截闸门、模型路由。只改其中一份，回溯时已无法回答「上周三那笔亏损当时是什么配置」。
更要命的是**回滚**：调参后变差想退回，却没有「原状」这个对象，只能靠人肉回忆改了哪几个键。
这不是可观测性不足，是**缺少版本概念**。

**落地形态**：
- 四单元各算**确定性指纹**（12 位短哈希），组合指纹对四单元再哈希
- 确定性要求：对象**键排序后**拼装、数值归一化（消除 `-0` 与浮点尾差）、
  **不含时间戳/id/运行期计数**——否则「配置没动但指纹变了」，回滚判定立刻失去意义
- 心法按 id 排序后再哈希：库内顺序不承载语义
- **拦截器 `order` 参与指纹**：闸门顺序会改变拦截结果（先拦几何还是先拦置信度，
  决定用户看到的拒绝理由），所以它是语义字段，不能剥掉
- 归档 `skipIfUnchanged` 默认开启：否则每次刷新都留一条一模一样的归档，
  索引很快被噪声淹没，**真正有意义的版本反而找不到**
- 索引损坏时**从快照文件重建**（`rebuildIndexFromArchives`）：索引是派生数据、
  快照是原始事实，派生数据坏掉时应该能从事实重建——这决定归档层能否被信任
- 一键回滚**回灌后重新采集指纹并比对**，不「写完就报成功」——
  任何「回滚了但引擎读到的还是旧值」的静默失败立刻暴露
- 导入只做校验 + 归档，**不直接回灌**：外部 JSON 不应有权直接改风控闸门
- 回滚只恢复心法的**启用状态**，不删改规则文本——规则文本是宪法红线的审查产物，
  回滚配置不应绕开那层审查

### 4.4 风控口径插值 → `server/riskBrief.ts`

**为什么内化**：LLM 提案器此前完全看不到执行层门槛，后果是双重的：
① **有效自由度被浪费**——模型按先验猜一个置信度（如 70），门禁是 80，报价被物理拦下，
模型既不知道为什么被拒也无法修正（此前观测到的「提案被拦但理由看不见」即属此类）；
② **口径分裂**——管理页把 R:R 从 2.0 调到 2.5 后，提示词若还写 2.0，
模型会持续产出必然被拒的报价，日志表现为「模型很努力但成交为零」，
真因却是**提示词与代码两套口径**。

**落地形态**：
- `renderRiskBrief()` 渲染 `【本周期风险预算】` 块，措辞含三层信息：
  ① 当前值（模型据此标定输出）② **这是执行层硬约束**（模型知道越界会被物理拦截而非「尝试执行」）
  ③ **已禁用的能力显式说「不得申请」**（加仓上限为 0 时明文禁止，否则模型仍会产出必然被拒的加仓申请）
- 必须读 `riskConstants.ts` 的**活绑定**，而不是 `riskConfig.ts` 的 DEFAULTS 表——
  后者是表单预填的静态默认值，读它会得到「面板显示的值」而非「引擎执行的值」
- `GET /risk/brief` 同时返回结构化值 + 渲染文本，**面板与提示词同源**
- 烟测里有防回归断言：提示词文本必须包含 `riskBriefSnapshot()` 里的实时阈值

### 4.5 原子写盘 → `server/atomicWrite.ts`

**为什么内化**：`writeFileSync(path, data)` 是「先截断、再写入」，
中间存在**文件已清空但新内容未落盘**的窗口。两种现实情况会命中：
① 进程被 kill（热重启、CI 超时、容器 OOM）；② 磁盘写满 / 配额耗尽。

被写坏的若是 `.env`，后果不是「丢一次配置」而是**全部风控参数回落到代码默认值**——
引擎将以用户从未批准过的敞口运行，而面板显示的仍是上一次成功读取的值。
**这类「配置静默降级」比崩溃更难排查。**

**落地形态**：同目录临时文件 → 写入 → `fsync` → `rename` 覆盖。
- `fsync` 不可省略：只 rename 不 fsync，操作系统可能把 rename 元数据先于文件内容刷盘，断电后得到长度为 0 的文件
- 临时文件名带 pid + 时间戳 + 随机后缀：同进程并发写、多进程共存都不互踩
- 失败路径**必须清掉临时文件**，否则崩溃循环会留下一地 `.xxx.tmp`
- 已替换 `loadEnv.ts` 的裸 `writeFileSync`；顺带修掉「文件以换行结尾时重建会多一个空行」的问题

## §5 · 明确不内化（含理由）

对标报告最容易变成「什么都想学」的清单。以下刻意**不内化**，理由如实记录：

| 项 | 不内化的理由 |
|---|---|
| **Python 插件热插拔执行用户代码** | R20 的插件是**同进程内执行的 Python**。EVOLVE 已明确「用户代码必须进程级隔离」这条红线（变异沙箱即为此而设）；为了热插拔而把用户代码拉回主进程，是用安全换便利。若要做，应做成**子进程 + 契约 RPC**，那是独立课题。 |
| **微积分动能引擎（v / a / κ）** | 理论上更敏锐，但**本项目当前连基础样本量都不足**（paper 模式运行时间短、成交样本少）。在没有足够样本验证「曲率阈值取 1.5 是否合理」之前引入三个新超参，只会增加调参噪声。**先把已有指标跑出统计意义，再考虑加维度。** |
| **同 base_url 优先的回退模型链** | 单 provider 场景下无收益；且 EVOLVE 的模型选择属风控行为（测试期统一用免费模型），引入自动回退会让「谁在做决策」变得不可追溯。待 multi-provider 真正上线再评估。 |
| **参谋委员会交叉质询（cross_examination）** | 我们的 Agent 团队尚未落席位配置层。质询的前提是「多个独立席位」，跳过席位配置直接做质询是本末倒置。列为待决而非内化。 |
| **R20 的参数取值本身** | R20 默认 `RISK_PER_TRADE_RATIO = 0.02`（2%/笔），EVOLVE 默认 0.01、稳健套件 0.005。**风格不同，不是谁的更对**。R20 面向小资金高周转，EVOLVE 当前 paper 模式以本金安全为先。裸抄阈值会掩盖这个差异。 |

## §6 · 待决项（需要用户决策，不擅自动手）

### 6.1 参谋委员会席位配置层
R20 的席位可配（`roles` 里每个席位有 `prompt` / `weight` / `temperature` / `reasoning_effort` /
`is_arbitrator`），支持 `standard` 与 `cross_examination` 两种议事模式，导出包**一个 JSON 文件
即可完整还原席位与议事规则**，导入前自动备份（保留最近 10 份）。
EVOLVE 的 Agent 团队设计（见 `DEV-PROMPT-KIT.md` Part K）已有角色划分，但**席位硬编码**。
**待决**：是否需要「席位可配 + 导入导出 + 备份轮转」这一层？还是先让 Agent 团队跑起来再谈可配性。

### 6.2 拦截器的可扩展性档位
现状：内置 TS 数组，用户不能新增。
可选路线：① 保持内置（最安全）② 加「参数化自定义闸门」（用户只填阈值，不写代码）
③ 子进程 Python/JS 插件（最灵活，成本最高）。
**待决**：在没有明确用户需求前，建议停在 ②——它覆盖 80% 的调参需求，且不引入执行不可信代码的风险。

### 6.3 R20 的每 6 小时进化调度
EVOLVE 的进化由自治循环按 K 线巡检驱动，没有独立的「定时全量复盘」调度。
R20 的 `single_evolution_cycle` 装饰器用 `fcntl.flock(LOCK_EX | LOCK_NB)` 保证
**同一时刻只有一个进化周期在跑**（重入直接跳过并记日志）——这个单飞语义值得借鉴，
但 Node 侧需换成对应的文件锁实现。
**待决**：是否引入独立进化调度 + 单飞锁。

## §8 · 给后来者的三条经验

1. **对标要读到源码级。** 媒体稿写的是「宽止损 + 0.8R 保本」，这是**我们早就有的能力**；
   真正有价值的 `risk_reservation` 的账本语义、`snapshot_observability` 的分档思路、
   `policy_snapshot` 的指纹确定性，全都不在宣传语里。**只看二手介绍会得出「我们已经够了」的错误结论。**

2. **学语义，不抄实现。** R20 是 Python 同步栈（sqlite3 + threading.Lock），
   EVOLVE 是 Node 单线程事件循环。`BEGIN IMMEDIATE` 的价值在「临界区不可分割」这个语义，
   而不在 SQLite 这个工具——照抄工具会引入不属于本项目的复杂度。

3. **内化过程要配烟测，且烟测要测语义不变量。**
   本轮 40 项断言里，**最有价值的一条恰好抓到了自己写的 bug**
   （§4.1 的 `occupying` 口径分裂）。如果只测「数值对不对」，
   这类「两套口径」的缺陷永远不会现形——而它正是本项目历史上反复踩的那类坑。
