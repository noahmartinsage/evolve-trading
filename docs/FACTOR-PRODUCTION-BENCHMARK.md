## §1 为什么对标（同构性论证）

用户提出的诉求是「AI 量化因子的批量生产能力达标商用生产级」。要判断差距，先要确认两边在回答**同一个问题**。

| 维度 | 上游（QuantSkills / PandaAI EVO） | 本项目（EVOLVE） | 是否同构 |
|---|---|---|---|
| **核心命题** | 把「交易想法 → 因子研究 → 策略生成 → 回测验证 → 风险评估 → 交易执行」组织成可复用工作流 | 同上（少了"想法录入"这一层，多了链上执行） | ✅ 同构 |
| **关键机制** | 因子是**框架中立的 OHLCV 函数**，成批生产 + 真实数据验证 + 索引去重 | 策略是硬编码的 6 族 27 个候选，评价靠回测曲线（fitness） | ⚠️ **不同构的那一半正是缺口** |
| **评价口径** | **截面** Rank IC / ICIR / 五分组多空 / 换手 / 半衰期 | 年化收益 / 最大回撤 / 每日笔数（fitness-v2） | ❌ **目标不同**（见下） |
| **决策/执行主体** | 人主导 + 多 Agent 协作（A2A），Agent 只在授权与风险边界内运行 | 编排层 + 提案引擎 + 晋级流水线，关键动作要人确认 | ✅ 同构 |
| **数据/执行场所** | A 股 / 港股 / 美股，通过券商与期货接口；数据来自 Pandadata | 加密货币永续（BTC/ETH），数据来自 Binance REST；执行经 CEX + 链上 DEX | ❌ 差异保留（后续优劣矩阵的依据） |
| **交付形态** | 每份能力是一个可安装的 **Skill 包**（给 Claude Code/Codex/Cursor 用） | 单一仓库内的服务与页面；语音层是唯一交互面 | ❌ 差异保留 |

### 同构性结论

**可以继续对标，但必须只对标"机制"，不对标"口径"。**

关键的一处不对称：上游做的是**截面**因子研究（A 股全市场几千只股票，逐日横截面排序 → 算 IC、分五组做多空组合）。本项目只有 BTC/ETH 两个标的，**截面宽度 = 2**，在 2 行数据上做横截面排序没有任何统计意义。上游 `skill-factor-decay/SKILL.md` 里明确写着「逐日截面评价：每一天对信号做一次截面 IC 计算，**不是时间序列 IC**」—— 那条要求针对的是"做截面研究却误用时序口径"，本项目没有截面可做，属**如实适配**而非照抄。因此本项目算的是**时序 IC**，且"分位差"只作诊断量，不是可交易的多空组合。

⇒ 这一条决定了 §5「不内化清单」里最大的一整块（截面化、行业中性、市值中性、逐日截面 OLS）不是"我们做不到"，而是**目标不同**。


这是上游自己给出的分类（导航仓库 README 的 category 02）。**这张表本身就是缺口清单**：本项目目前只有"因子生成 + 因子评价"两块，且评价口径是时序列，其余四块（筛选报告、正交化、衰减、合并）完全缺失。

### 2.3 三个值得学的设计细节

**① 验证必须吃真实缓存数据，且"不得把合成验证描述成真实验证"**

`skill-quant-factor-skill-factory/SKILL.md`：

> Validation must use cached real OHLCV data when available. **Do not describe synthetic validation as real validation.**
> Do not claim Yahoo data is present unless `real_market_data/raw/yahoo_us/*.parquet` and the panel manifest prove it.

这是**可执行的证据契约**，不是免责话术：它要求"声称某份数据在"必须由面板清单证明。本项目 `server/evidence.ts` 从 09-14 起就持同样立场（合成 GBM 上过了回测不构成进实盘依据），本轮把它**扩展到了因子线**。

**② 验收清单是机器可查的，而不是"看起来对"**

`references/acceptance_checklist.md` 的验收项：生成目录数 == 请求数、`validation_summary_real.json` 行数 == 请求数、所有行 `status == "pass"`、**合并索引无重复 slug**、抽样跑第一个/中间/最后一个的 `validate.py`。

注意第 4 条：**去重是验收项，不是实现细节**。上游把它列为"没做到就不算交付"，这正是本项目最贵那类缺陷（同一事实两份）的防线。

**③ 基因空间与"重复生产"的边界**

`generate_factor_skill_batch.py` 的核心是三层笛卡尔积：

```
33 个基础机制 × 8 个变换 × 10 个窗口 = 2,640 个候选
（变换含：标准化 z / 变化 delta / 平滑 smooth / 时序排名 rank / 波动缩放 / 稳定度 / 量能确认 / 压缩）
```

去重口径是 **slug 唯一**（`name_en` 规范化后的字符串）。

★ **这里有一个上游没有解决的问题，本项目抓到了**：`z`（标准化）与 `rank`（时序排名）在**秩相关**口径下与原始因子完全等价（单调变换不改变排序），`compress`（tanh）同理。所以上游那 2,640 个候选里，有相当一部分是"换了马甲的同一个因子"。本项目因此做了两件事（见 §4）：生成端**不产出仿射变换**，评价端加一道**秩相关去冗余闸门**。实测在 40 个候选里，这道闸门拦下 **15 个**。

**④ 三态缺一档：上游只有"通过/复核"，没有"证据不足"**

`blind_mining_workflow.md` 的立场是：

> Treat these as diagnostics rather than universal hard thresholds.

这个立场对"研究辅助工具"是对的（不该用硬阈值替研究者下结论），但对"要进真实资金的生产线"是危险的：它没有 `UNVERIFIABLE` 这一档，于是"样本不够"和"因子不行"会被混成同一句话。本项目保留自己的 fail-closed 立场（见 §3）。

## §4 已内化清单

本轮内化 4 项，全部有语义不变量烟测（`scripts/factor-smoke.ts`，10 场景，已进 CI）。

### 4.1 因子成为一等实体 + 批量生产（`src/engine/factorEval.ts`）

**原来怎么错**：系统里没有"因子"。判一个候选好坏的唯一尺子是 `fitness-v2`，而它只看年化收益/最大回撤/每日笔数 —— 那是**一条回测曲线**的总结，不是**一个信号**的性质。于是「信号没用」与「信号有用但被交易成本吃掉」在系统里长得完全一样（都是 fitness 低），没人知道该改哪一头。

**现在**：14 个基础机制 × 5 个变换 × 7 个窗口 = 490 个候选空间，按固定顺序展开，跳过索引里已有的 slug；每个因子算 coverage / 多期限时序 Rank IC / ICIR / 分位差 / 换手。

**刻意不产出** `z`（标准化）/`rank`（时序排名）这类**仿射/单调**变换 —— 秩相关口径下它们与原始因子等价，产出它们只是把 33 个机制放大成 2,640 个名字（见 §2.3③）。

### 4.2 三态闸门 + 可注入阈值（`judgeFactor`）

**闸门顺序**（顺序本身是被断言的，不能重排）：

| 序 | 闸门 | 不通过时的档位 | 理由 |
|---|---|---|---|
| ① | `lookahead` | `rejected` | 偷看未来是**代码缺陷**，与数据来源无关。诚实的合成数据配上偷看未来的因子照样必须拒 |
| ② | `lookahead-unknown` | `unverifiable` | **`null` 不是 `false`**。写成 `if (!lookahead)` 会把"没检查"变成"检查通过" |
| ③ | `origin` | `unverifiable` | 非真实历史一律不放行。合成 GBM 里不存在可被捕捉的结构 |
| ④ | `bars` | `unverifiable` | 样本不足 → 没资格下结论（fail-closed） |
| ⑤ | `coverage` | **`rejected`** | 只在 3% 的根上有值的因子不是"核不了"，是它确实不产出信号 |
| ⑥ | `turnover` / ⑦ `duplicate` / ⑧ `ic` / ⑨ `icir` | `rejected` | 确定性的"不行" |
| — | `icir-unknown` | `unverifiable` | 分块不足或分块 IC 无离散度 = 证据不足，不是"因子不行" |

阈值全部走参数（`DEFAULT_FACTOR_GATE`）；端点**刻意不接受请求体传阈值** —— 允许调用方传阈值等于门可以自己开。

实测灵敏度（`test:factors` F5）：6 个阈值逐条推到极端，结论**逐条按预期翻转**；全部放开时同一份指标必须通过（反向对照，防止"门坏了"伪装成"阈值被读到"）。

### 4.3 判决与数据来源绑定 + 台账唯一性（`server/factorService.ts`）

- 取数**复用 `server/evidence.ts` 的 `loadEvidence()`**，不另写取数函数。理由是硬的：如果因子线与门禁线吃不同的数据，那么"因子通过了"与"策略没过门"永远无法互相解释，两边都会坚称自己算得对（F-47 已因同一原因拒绝过一次捷径）。烟测 F10 直接断言两边指纹相同。
- 台账每一行带 `origin` + `dataHash`。**没有 `dataHash` 就看不出来"换了数据，旧结论不再适用"**。
- 写盘前 `assertIndexUnique`：重复 slug 直接抛。上游把它列为验收项，这里做成了写路径的硬约束。
- 读取损坏的台账 → 返回空索引但把 `damaged` 标出来，**不抛**：读路径抛异常会让"台账坏了"表现为"整个面板打不开"，后者掩盖前者。

### 4.4 修掉一处真实故障：提案引擎与门禁吃两套数据（`server/proposalEngine.ts`）

**原来怎么错**（这是本轮最值钱的发现，也是"我已在承受的真实故障"）：

```
提案引擎  buildCandles()  → 种子按小时轮换的合成 GBM      ← 挑选在这里
门禁      evidence.ts     → data/history/*.json 真实历史   ← 判决在这里
```

两个具体且已发生的后果：
1. 合成 GBM 里不存在可被策略捕捉的结构（`evidence.ts` 开篇的实测表已把这条钉死：合成数据上 PBO=9.1% 但选择净收益 −33.0）。在这一套数据上按 fitness 取 Top-N，取出来的是**噪声排名**，不是"候选里最好的那个"。
2. 种子每小时换一次 ⇒ 同一批候选每隔一小时得到一套不同排名，产出的提案与写进心法库的经验都在跟着漂，**事后无法复现任何结论**。

**现在**：优先真实历史（`loadEvidence`），并把来源标进 `GenerateResult.dataOrigin`（可观测）。注入 K 线时标 `injected`，无历史时才回落合成并标 `synthetic`。烟测 F10 断言：真实历史存在时，提案引擎**不得**仍在合成行情上挑选候选。

★ 顺带修掉一处**文案与实现不符**：`server/voice/awareness.ts` 里介绍实验室能力的那句写着"让提案引擎在**真实 K 线**上跑一轮候选评估"—— 而在这条修复之前，那句话是**不成立的**。现在它成立了。

## §5 明确不内化（含理由）

| # | 项 | 不内化的理由 |
|---|---|---|
| 1 | **截面化**：截面 Rank IC、五分组多空、行业中性、市值中性、逐日截面 OLS 正交化 | **目标不同**。本项目只有 2 个标的，截面宽度 = 2，几何上做不出有统计意义的排序。把上游的截面报告照搬过来会产出**一堆看着很专业的无效数字** —— 比没有更危险 |
| 2 | Pandadata / jqdata / tushare 数据依赖 | 上游是 A 股研究栈；本项目数据源是 Binance REST、执行场所在 CEX 与链上。引入 A 股数据层与本系统目标无关，且会引入第三套行情口径 |
| 3 | 遗传/梯度搜索（三阶段进化候选空间 + 精英/交叉/变异） | **前置条件未满足**。遗传搜索的收益建立在大样本上；在 30 天数据上跑它等于**在噪声上做更快的优化** —— 而 PBO=40.1% 已经在说噪声本来就压不住。先攒样本（§6-1），再谈搜索算子 |
| 4 | 因子 Skill 打包契约（8 个固定文件 + `agents/openai.yaml` + 双语文档 + `validate.py`） | **上游的取值只是风格不同，不是对错**。那套形态解决的是"把一个因子作为可分发的社区资产交付给陌生人的 Claude Code"；本项目是单一仓库内自用生产线，打包成本换不到任何收益。（若将来要把因子作为资产对外分发，这一项应重新评估） |
| 5 | 上游"阈值是诊断而非硬阈值"的立场 | 与既有红线冲突。研究辅助工具不该替研究者下结论，但**要进真实资金的产线必须 fail-closed**。缺 `UNVERIFIABLE` 这一档会让"样本不够"和"因子不行"混成同一句话，而两者的正确处置完全相反 |
| 6 | Papers With Backtest / Quantpedia 的因子与策略目录本身 | 它们是**内容**不是**机制**。内化机制（IC 口径、去冗余、报告格式），不搬运内容 —— 公开的因子公式随使用者增多必然拥挤（这一点连上游创始人都公开承认） |
| 7 | Global Factor Data | **结论不可得**：`bkelly-lab/GlobalFactorData` 返回 404。没有源码级证据就不下结论，不靠二手介绍补 |

## §6 待决项（需用户裁决，本轮未擅自决定）

1. **样本量是首要瓶颈，且没有技术捷径。** 现有真实历史 = 2 标的 × 2,880 根 15m（2026-07-24 → 08-23，零缺口）。要不要现在跑 `npm run data:fetch` 把历史拉到 6~12 个月？这是解锁"因子→策略→真钱"的唯一路径，**不是放宽阈值**。
2. **生产目标是"数量"还是"质量"？** 现在是"按请求数量展开候选，通过多少算多少"（实测 40 个候选通过 4 个）。要不要改成"产出直到攒够 N 个通过"，以及 N 取多少？
3. **IC 符号怎么消费？** 当前判门用 `|IC|` 与 `|ICIR|`，因此**稳定负 IC 的因子会被接受**（本轮实测通过的 4 个因子 IC 全为负 —— 这 30 天 BTC 是均值回复的）。消费方（提案引擎/决策大脑）是否按符号取反使用？这需要一条明确的策略，否则一个"稳定反向"的因子会被当成"正向信号"用。
4. **因子要不要接进策略生产？** 现在是两条并行产线：因子线只出台账，策略线只出提案。真正的"批量生产"应该是 `accepted 因子 → 候选策略的信号源`。要不要做这条接线？
5. **台账要不要上界面？** 当前只有端点（`POST /factors/generate` / `GET /factors/index`）+ 语音可读（问"进化实验室能干什么"会报道台账概况）。要不要在进化实验室页加一块？
6. **下一批对标对象？** 上游 214 项资产、44 项在"因子研发工具箱"，本轮精读了 5 项。建议下一批：**因子筛选（报告体系）** 与 **因子池与在线化（生命周期）** —— 都是"配置成熟度"类，补起来快。

## §8 给后来者的经验

1. **先做同构性论证，再读源码。** 上游是截面研究、我们是时序 —— 如果跳过 §1 直接照抄 IC/分组/正交化，会得到一堆**看起来非常专业、但在这个系统上没有意义**的数字。这类输出比"没有"更危险，因为它会被人当成证据使用。

2. **上游去重按字符串，重复生产的真身是"秩相关 1.000 的不同名字"。** 实测：`ret_compress`（tanh）与 `ret_raw` 秩相关 **1.000**，`reversal` 与 `ret` 是 **−1**。上游 2,640 个候选里到底有多少是同一种东西，是个没被回答的问题。⇒ 去重必须用**评价口径下的等价关系**（秩相关），不是名字。

3. **"数据的来源"必须是一等事实，不能是注释。** 本轮最值钱的发现就是一处数据来源分裂（挑选吃合成、判决吃真实）。它不报错、不崩、每个模块单看都对，表现只是"提案质量莫名其妙地差"。修法不是加日志，是让这个事实**进入返回值**，然后断言它。

4. **测试夹具自相矛盾会伪装成产品缺陷。** 我把"放开所有闸门"的常量 `GATE_OPEN.maxDuplicateCorr` 设成 1.5，然后拿**同一份配置**去验证"反号因子会被拦下"—— 当然拦不下，而失败信息写着"去冗余没生效"。**「全部放开」与「除某一项外全部放开」是两份不同的夹具。**

5. **三态里的第三档必须有名字、有理由、且**能被断言**。`lookahead` 返回 `true | false | null`，判门对 `null` 单独出一档 `unverifiable`。如果写成 `if (!lookahead)`，那么"这条检测根本没跑起来"会静默变成"检测通过"——本仓库同类缺陷已复现多次。

6. **门禁的红必须能分辨真假。** 本轮 CI 第一次跑是红的，真因是**我自己新写的 `drawdown` 因子**用了 `let peak` 被 lint 的 `no-useless-assignment` 抓到 —— 与因子逻辑无关。若当时按"因子系统有问题"去查，会浪费很久。

7. **环境里有几个会伪装成逻辑错的坑**（本轮又踩一次）：同一条消息里对同一个文件发两个 `Edit`，**前一处会被静默丢弃**。本轮症状是变异报告显示"M4 期望 F3 实际 F2"，看起来像脚本逻辑错，实际是我那条 `expect` 修改没落盘。
